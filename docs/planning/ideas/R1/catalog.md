### critic-01 半ずれ段で白黒鍵対（VMPK 型 2 段×2）　先出し◯（§1 D）

- 根拠: VMPK g_DefaultKeyMap（Z=12…P=40、約 2.5 オクターブ）confirmed。Deskthority 段ずれ 1/2・1/4・1/2 confirmed。S は Z–X の中点、2 は Q–W の中点（算術で整合）。文字・数字キーは JIS/US で同位置。反する: ノート PC（出荷 87.7%）が均等 1/4u ずれなら中点の前提が崩れる。縦比は六角 0.866 対 物理 1.0 のままずれる。数字段を黒鍵にすると数字入力・YouTube の数字シークと衝突（disablekb=1 で抑止）。両手を上下に重ねる操作感は未検証。
- 難所: 利用者の段ずれ型をブラウザから知る手段が無い。pipeline-08 の Z/A だけなら 1 オクターブ強で曲が狭く、core-02 の 2 段×2 なら右手が左手の上段に重なる。

### critic-02 段ごとの着地線と奥行き　先出し◯（§1 A「レーンの高さ違い」、§1 B）
- 統合: critic-02、core-09（段ごとに着地線）、feel-03（三段ハニカム判定帯）
- 要約: 判定線を 1 本に揃えず、鍵盤図の段ごとに 3/4·h（または 1u）ずつ高さの違う着地帯にし、セルは自分の段のスロットに重なった瞬間が判定。落下域の上端も段ごとに上げて可視時間を揃える。手前の段ほどセルを大きく描き、重なりは手前が上。判定は時刻だけ。
- 根拠: 「セルに着地」方式が試作 m1 に既にある。Red Blob 3/4·h confirmed。IIDX の LIFT、lazer の判定位置補正、jubeat の固定パネル到達判定、Banquiero 2024 の鍵ごとに落ちる MR。物理では Q 段と A 段の同列キー中心が 1/4u しか離れず、1 本線だと幅 1u のセルが約 75% 重なる（算術）。反する: 同時刻のセルが横一線に並ばず和音の同時性が高さで読めなくなる（段差 3s＝125〜250 ms 相当）。落下域上端が階段になり YouTube プレイヤーとの境界が凸凹。
- 難所: 「同じ高さ＝同時」の手掛かりが消える。塊描画（tech-04）で同時性を補う前提になる。
- 点数: 価値 3／実現 5／芯 5 ＝ 13（feel-03 の値。critic-02 は 3/4/4、core-09 は 3/5/4）

### core-05 回転で着地を合わせる／嵌合の重なり採点
- 統合: core-05、feel-02（嵌合の重なり採点）
- 要約: 早遅をバーや文字で別の場所に出さず、着地したセル自身に残す。(a) core-05: 着地前 300 ms で 60° 回し、押した瞬間の角度（±30 ms＝6°）で止めて 200 ms 残す。(b) feel-02: 判定線を鍵盤側の六角スロットにし、セルが嵌まる瞬間の縦の隙間（1 ms＝0.5 px）を連続採点にして隙間側の辺だけ光らせる。
- 根拠: 正六角は 6 回対称（confirmed）。jubeat のセル内マーカー、osu! のアプローチサークル、Wife3 の erf 連続採点、FNF PBOT1 のシグモイド confirmed。反する: 時刻源は 15 ms 刻み・逆行 ≤10 ms、rAF 1 フレーム 3.3° なので ±20 ms 以下の差は描画分解能以下。feel-02 の 95/80/50% 閾値は h=56 で ±5.6／22／56 ms に当たり最上位が相場（±16〜33）より狭く、feel-07 の ±30 と食い違う。4° が見えるかの知覚データ無し。セルの文字も一緒に回る。
- 難所: 回転・隙間は判定結果から逆算して描く必要がある（描画時計と判定時計が別）。量子化由来の隙間が「自分のせいでないずれ」として光る。
- 点数: 価値 3／実現 4／芯 5 ＝ 12（feel-02 は 3/4/4＝11）

### core-07 拍を六角の行で刻む（1 拍＝n 段）

- 難所: 端レーンの画面外処理と、flat-top 落下域で代替できるなら傾ける理由が残るか。
- 点数: 価値 2／実現 4／芯 4 ＝ 10

## 2. 入力と配列（鍵割り当て・同時押し・環境差）

### core-03 Wicki–Hayden 等方性配列モード　先出し◯（§0 等方性、§1 C、§2 配列プリセット）

### pipeline-04 難から間引く難易度生成と自己検査　先出し◯（§3 難易度別の間引き・4 軸、§3 検証）

### pipeline-01 手元音源のブラウザ採譜（私的モード・信頼度付き）　先出し◯（§3(b) ローカル音源の採譜）

### pipeline-02 試奏で動画に整列／弾いて録るエディタ　先出し◯（§6 譜面エディタ・自由演奏の録音譜面化）
- 統合: pipeline-02、pipeline-13（弾いて録るエディタ）、wander-13（演奏が譜面になる）
- 要約: 既にある音符列（MIDI や採譜結果）を YouTube の時間軸に合わせるのに、動画を 0.5〜1.0 倍で流しながら利用者の試奏を記録し、楽譜音符列×打鍵列の DTW で楽譜時間→動画時間の区分線形写像を得る。譜面が無い曲は打鍵ログ（キー・動画時刻）をそのまま譜面にし（Specy の recorded 形式）、2 回弾いて 50 ms 以内に一致した音だけ残す。その後は六角フィールドをクリックして置く・消す、Ctrl 1 ms／Shift 10 ms の微調整（osu! 型）。seekTo 後 210〜260 ms の再進行待ちを見込んでループ頭に 300 ms の空白。
- 根拠: TISMIR 2023（楽譜×演奏 MIDI の整列 F 98.5%、拍アンカー付き 99.9%、±100 ms まで一貫）、parangonar の AnchorPointNoteMatcher、StepMania の SD ゲート、osu! エディタの刻み、ArrowVortex の半拍ずれボタン、Specy recorded、Falling Nikochan の ytBegin/offset、setPlaybackRate 非保証と 8 段階、seekTo 実測 confirmed。反する: TISMIR の数値は熟練ピアニストの古典演奏で、素人×ポップスは未検証。osu! は「できれば再生速度を落とさない」。試奏の打鍵時刻にはキーボード 15〜60 ms・反応の遅れが一律に乗り、0.5 倍で録ると曲時間上の遅延が 2 倍。低速再生時の音高保持は未確認。動画が楽譜と違う構成（繰り返し・間奏）のときの DTW の破綻検出。
- 難所: 反応遅延の平均成分と動画との真のずれの分離（問い 7）。構成違い動画の検出。iframe へのフォーカス漏れ。

### tech-01 二つの時計の補間同期（判定時計の単調補間）　先出し◯（§7 音ズレ）

### social-01 入力ログ型リプレイとゴースト　先出し◯（§6 リプレイ・ゴースト対戦）

- 難所: ログの時刻基準と動画時刻への写像誤差。ハッシュの境界。クライアント生成ログの信頼性。

### critic-08 譜面は別経路・音は埋込（同梱 30 曲）　先出し◯（§3 YouTube は再生にだけ、§3(a) MIDI 持ち込み）

## 8. 技術（描画・配布・基盤）

### tech-08 Worker 描画と入力分離
- 要約: 描画は OffscreenCanvas を Worker に転送して Worker 内の rAF で行い、メインは keydown の受付と YouTube API だけ。入力は Event.timeStamp 付きで SharedArrayBuffer のリングに書き Worker が判定。PixiJS 8 でスプライト＋グリフアトラス。cross-origin isolated にすると timeStamp が Chrome で 0.005 ms になるが、その状態で YouTube iframe が読めるかは不明（<iframe credentialless> を試す）。
- 根拠: OffscreenCanvas Baseline 2023-03、rAF timestamp、timeStamp の隔離時精度、PixiJS 8.22 MIT、WebGPU 対応表、keydown の即時配送 confirmed。反する: timeStamp は事象生成時に付くので Worker 分離で精度は変わらず、改善するのは GC・長タスクの影響だけ。SAB は cross-origin isolation を要求し、COEP: require-corp では YouTube iframe が読み込まれない見込み（demucs-web と同じ要件）。研究内に Worker＋OffscreenCanvas の音ゲー事例は無い（Bemuse 等はメインスレッド）。YouTube の時刻読みはメインスレッドでしか取れず Worker へ送る経路が要る。
- 難所: cross-origin isolation と YouTube iframe の同居。分離の利益が通信で相殺されないこと。
- 点数: 価値 2／実現 2／芯 1 ＝ 5

### tech-16 PWA と Tauri の二段配布　先出し◯（§6 オフライン対応・デスクトップ化）
- 要約: 本体は PWA（マニフェスト＋Service Worker）で譜面・ピアノ音源・校正プロファイルをオフラインに持つ。YouTube 曲はオフライン再生が規約で禁じられるので、オフライン時は自前音源曲と鍵盤音だけの練習に限定。希望者向けに Tauri 2 の殻（MIDI フォルダ監視、OS の音声出力遅延取得、常時前面）。Mac で Web MIDI を使うなら Electron。
- 根拠: PWA マニフェスト、Tauri 2 MIT/Apache（OS WebView）、Electron 45、Web MIDI の Safari 非対応、III.E.1.b・III.I.9、Synthesia の持ち込み、JEITA ノート 87.7% confirmed。反する: オフラインで YouTube iframe が onError を返すとは限らない。cpal で得られるのはバッファ長で実出力遅延そのものではない（要確認）。WebView2／WKWebView の機能差（Web MIDI・OffscreenCanvas・WebGPU）は未取得。学校端末では管理者ポリシーでネイティブ導入が制限されることが多い（記憶）。
- 難所: 配布先が二つになり QA が倍。Service Worker のキャッシュ更新と大きな音源の版管理。
- 点数: 価値 2／実現 3／芯 1 ＝ 6
